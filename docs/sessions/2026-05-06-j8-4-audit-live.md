## Incidents / anomalies

### Bug — CLOSE-WAIT spin loop : daemon Holmes MCP à 76% CPU

**Contexte** : lors du smoke test HTTP, plusieurs scripts Python (mcp_smoke2/3/4, httpx, curl)
ont tenté de se connecter au serveur MCP via POST `/mcp`. Chacun a été interrompu
par un `timeout` ou une exception réseau, fermant la connexion TCP côté client de façon
abrupte (SIGKILL du process ou `--max-time` curl).

**Symptôme** : daemon en état `R` (running) à 76% CPU, ne répondant plus aux nouvelles
requêtes HTTP (GET `/mcp/` → timeout). 2 SIGKILL requis (autorisés par PO).

**Diagnostic** (collecté avant le 1er SIGKILL) :

| Observation | Valeur |
| --- | --- |
| `wchan` | `0` (pur userspace, pas de syscall) |
| `syscall` | `running` (event loop asyncio en spin) |
| FDs ouverts | 10 (1 epoll, 4 sockets listen/worker, 1 ESTAB) |
| Sockets sur port 8765 | 7 sockets en **CLOSE-WAIT** avec Recv-Q 472–479 bytes |

**Cause racine** :

Les connexions HTTP interrompues par `timeout` / `kill` envoyaient un TCP FIN côté client,
laissant le serveur uvicorn en état `CLOSE-WAIT` (FIN reçu, côté serveur pas encore fermé).
Les données en Recv-Q (≈ 470 bytes = corps HTTP non lu) signalent continuellement epoll
comme "readable". L'event loop asyncio de FastMCP itère sur ces sockets en boucle serrée —
lire les données, échouer à répondre (connexion morte), recommencer — sans jamais fermer
le socket ni le sortir de la watch-list epoll.

**Bug FastMCP** : `StreamableHTTPServerTransport` ou la couche uvicorn ne gère pas le
passage `ESTABLISHED → CLOSE-WAIT` pour les connexions SSE. Il devrait détecter le FIN
client (read() retourne 0 octets ou EOF), fermer le socket et nettoyer la session MCP.
Au lieu de ça, le socket reste en CLOSE-WAIT indéfiniment dans la watch-list epoll.

**Reproductibilité** : 100% — toute connexion interrompue avant de recevoir la réponse
SSE complète déclenche ce comportement. Confirmé sur la même session avec le 2e daemon
(PID 988611) qui est aussi monté à 69% CPU après 3 nouvelles tentatives.

**Workaround appliqué** :
- SIGKILL (autorisé PO) → Jeedom auto-redémarre le daemon
- Smoke test effectué via `build_mcp()` (import direct, sans HTTP)

**Action recommandée** : ouvrir un issue FastMCP sur le repo anthropics/fastmcp.
Mitigation possible côté Holmes MCP : `SO_KEEPALIVE` avec timers courts sur le socket
uvicorn pour détecter les connexions mortes plus vite.
