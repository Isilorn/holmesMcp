## Découvertes et décisions

### Bug 1 — Cause racine du CLOSE-WAIT : `McpActivityLogger._buffered_receive`

**Symptôme** : `session.initialize()` timeout à 10s, puis daemon à 89% CPU en CLOSE-WAIT spin.

**Cause** : `McpActivityLogger` bufférise le body de la requête puis passe une fausse
fonction `_buffered_receive` à FastMCP. Cette fonction retournait immédiatement
`{'type': 'http.request', 'body': b'', 'more_body': False}` pour tout appel après le premier.

FastMCP, après avoir traité la requête, appelle `receive()` en boucle en attendant
`{'type': 'http.disconnect'}`. En recevant des `http.request` vides à chaque appel (sans
vrai yield I/O), il bouclait en permanence — bloquant le SSE, puis provoquant CLOSE-WAIT
quand le client déconnectait.

**Fix** : relayer les appels suivants vers le vrai `receive()` d'uvicorn :
```python
async def _buffered_receive():
    if not body_sent:
        ...
    return await receive()   # ← relais au vrai receive pour http.disconnect
```

**Impact** : ce bug existait depuis J6-1 (création de McpActivityLogger). Il ne se
manifestait pas pour les `tools/call` (FastMCP retourne sans attendre disconnect), mais
bloquait systématiquement `initialize` (FastMCP attend le disconnect avant de finaliser).

### Bug 2 — `asyncio.run(_serve())` vs `uvicorn.run()`

Le plan J8-4bis suggérait `asyncio.get_event_loop().create_task()` avant `uvicorn.run()`.
Ce pattern est incorrect (boucle non démarrée). Implémenté correctement via :
```python
async def _serve() -> None:
    asyncio.create_task(_watchdog_close_wait(ARGS.port))
    config = uvicorn.Config(authed_app, ...)
    server = uvicorn.Server(config)
    await server.serve()
asyncio.run(_serve())
```
Watchdog s'exécute dans la même boucle qu'uvicorn. Aucune différence fonctionnelle
vs `uvicorn.run()`.

### Note — Watchdog Level 2 vs Fix activity.py

Le watchdog est un garde-fou pour les CLOSE-WAIT résiduels (RST, crash client, etc.).
Le fix `activity.py` prévient la MAJORITÉ des CLOSE-WAIT en permettant à FastMCP de
détecter le disconnect proprement et de fermer le socket avec FIN/ACK.
Les deux mécanismes sont complémentaires.
