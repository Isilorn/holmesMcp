# ADR-0023 — La remontée expression → scénario est récursive

- **Date** : 2026-09-16
- **Statut** : accepted
- **Amende** : ADR-0017 (Sanitisation et guardrails) pour la partie `config` et colonnes calculées
- **Origine** : signalement du projet `jeedom-skills` (jalon M0 de sa migration V2.0.0), vérifié et
  quantifié sur la box le 2026-09-16

## Contexte

`jeedom-skills` a établi la baseline « Phase 0 » de sa migration en rejouant ses 13 workflows avec
son ancienne couche d'accès (SSH + MySQL direct). Ce travail a mis au jour deux défauts de cette
couche V1 et a demandé si Holmes MCP les reproduisait — la question étant qu'en cas de défauts
concordants, la comparaison avant/après validerait deux erreurs au lieu d'en détecter une.

### Le fait de schéma

`scenarioElement` ne porte **aucune** colonne de rattachement au scénario : ses colonnes sont
`id`, `order`, `type`, `name`, `options`, `log`. Le lien vit dans le JSON
`scenario.scenarioElement` — mais **ce JSON ne liste que les éléments racines**. Un élément
imbriqué s'atteint depuis son parent par une expression `type='element'` dont l'`expression`
porte l'id de l'enfant.

Sur l'installation de référence : **116 racines pour 374 éléments — 69 % des éléments sont
imbriqués**, jusqu'à cinq niveaux de profondeur.

Toute remontée « quelle expression appartient à quel scénario ? » est donc **récursive**. Il n'y a
pas de raccourci correct, et les deux raccourcis tentés se sont trompés :

| Jointure | Faux positifs | Faux négatifs |
|---|---|---|
| `s.scenarioElement LIKE CONCAT('%', sel.id, '%')` (`_domain/usage_graph.py`) | **oui** — l'élément 1 matche `["100","218"]` : 199 paires inventées, 21 scénarios faux sur 63 | oui |
| `JSON_SEARCH(s.scenarioElement, 'one', CAST(sel.id AS CHAR))` (`tools/equipments.py`) | non — comparaison exacte | **oui** — racines seulement : **91 liens rendus sur 289, soit 31 % de rappel** ; 87 commandes sur 165 rendaient 0 alors qu'elles sont utilisées |

Dans les deux cas, **aucun avertissement** : la réponse était fausse et plausible.
`false_positive_warnings` n'était alimenté que par les blocs `code` PHP.

### Trois défauts trouvés en chemin

- **`SELECT COUNT(*) FROM scenario` rendait `***FILTERED***`**, pas un compte : le mécanisme 1
  (whitelist par table) masque toute colonne absente de la whitelist, et une colonne **calculée**
  n'appartient à aucune table.
- **Le mécanisme 1 était inerte sur `eqLogic`, `dataStore` et `historyArch`** via `query_sql` :
  l'extraction du nom de table normalise en minuscules (`eqlogic`), et les clés de la whitelist
  sont en casse Jeedom — le `dict.get()` échouait silencieusement.
- **La table `config` rendait ses valeurs en clair** quand la requête ne sélectionnait pas la
  colonne `key` : le verdict de sensibilité se lit sur cette colonne, absente ⇒ plus rien à juger.
  Vérifié sur données réelles (booléens seulement) : `SELECT value FROM config WHERE key='api'`
  rendait les valeurs, là où `SELECT key, value …` les masquait.

## Décision

### 1. Une remontée récursive unique, partagée

`_domain/scenario_tree.py` expose une CTE `WITH RECURSIVE` (MariaDB ≥ 10.2, la box est en 10.11)
qui part de l'expression et remonte de parent en parent jusqu'aux racines :

```sql
WITH RECURSIVE anc (expr_id, ss_id, node_id, depth) AS (
    SELECT x.id, ss.id, ss.scenarioElement_id, 0
    FROM scenarioExpression x
    JOIN scenarioSubElement ss ON ss.id = x.scenarioSubElement_id
    WHERE <seed>
  UNION
    SELECT a.expr_id, a.ss_id, ss2.scenarioElement_id, a.depth + 1
    FROM anc a
    JOIN scenarioExpression x2  ON x2.type = 'element'
                               AND x2.expression = CAST(a.node_id AS CHAR)
    JOIN scenarioSubElement ss2 ON ss2.id = x2.scenarioSubElement_id
    WHERE a.depth < 20
)
```

Le **test de racine reste `JSON_SEARCH`** : c'est lui qui garantit l'absence de faux positifs, et
il est éprouvé. On n'ajoute que ce qui manquait — la remontée. `UNION` (et non `UNION ALL`)
déduplique, donc un graphe cyclique ne peut pas boucler ; `depth < 20` borne malgré tout.

Cinq requêtes adoptent ce fragment : `find_command_usages`, `find_equipment_usages`
(`tools/equipments.py`), `_EXPR_REFS`, `_CODE_REFS`, `_SCENARIO_CALLERS`
(`_domain/usage_graph.py`, donc `find_scenario_dependencies`).

**Rejeté** : une remontée en Python (N+1 requêtes, et la logique se serait dédoublée entre les
deux modules). Mesure : 18 ms par appel en CTE, sur 374 éléments.

### 2. La troncature est déclarée

`query_sql` renvoie `limit_applied` et `truncated`. `truncated: true` signifie « le nombre de
lignes a **atteint** la limite » — conservateur par construction : jamais de sous-déclaration.

### 3. Les agrégats sont lisibles, sans ouvrir la whitelist

`sanitize_row`/`sanitize_rows` acceptent `allow_columns`, qui complète le **mécanisme 1 seulement**
(les mécanismes 2/2bis/3 continuent de s'appliquer). `query_sql` ne peuple cet ensemble qu'avec :

- `COUNT(...)` — une cardinalité ne rend jamais la valeur, quel que soit son argument ;
- `SUM/AVG/MIN/MAX/GROUP_CONCAT(col)` **si et seulement si** `col` est déjà exposable pour la table.

Tout le reste — alias simple (`SELECT value AS n`), concaténation, `CASE`, sous-requête — reste
filtré. Le contournement par alias est couvert par un test dédié.

### 4. La whitelist est insensible à la casse, et `config` échoue fermé

`whitelist_for()` indexe les whitelists en minuscules. `_sanitize_config_row()` masque `value`
quand la row ne porte pas `key` : sans la clé, le verdict est impossible, donc on masque.

Mais **fail closed ne doit pas vouloir dire « débrouille-toi »**. `SELECT value FROM config
WHERE plugin=…` est une requête raisonnable, et exiger de connaître les clés d'avance rendrait
l'outil hostile. `query_sql` **ajoute donc `key` au SELECT** quand elle manque — même esprit que
le `LIMIT` injecté et les backticks automatiques — et le signale dans `note`, la requête
réellement exécutée restant visible dans `query`.

L'injection est refusée là où elle changerait le sens de la requête (`SELECT *`, `DISTINCT`,
agrégat, expression) : ces formes restent masquées, avec une note qui dit quoi faire. Le tool
`get_config(plugin, key_pattern)`, lui, n'a jamais été concerné — ses quatre requêtes
sélectionnent toujours `plugin, key, value`.

## Conséquences

- **Les réponses changent.** `find_command_usages` passe de 31 % à 100 % de rappel sur
  l'installation de référence ; `find_scenario_dependencies` corrige 21 scénarios sur 63. Toute
  baseline établie avec les versions ≤ 1.2.1 est à rejouer — c'est le cas de la Phase 0 de
  `jeedom-skills`, prévenue.
- **`SELECT value FROM config` renvoie une colonne de plus** que demandée (`key`), et la réponse
  porte une `note` qui l'explique. Vérifié sur la box : les clés sensibles restent masquées après
  réparation.
- Les tests d'intégration live ne figent aucun identifiant de l'installation : ils **recalculent**
  la vérité par une remontée de référence indépendante et comparent. Un contrôle positif seul
  mesure la sensibilité, pas la précision — c'est ce qui avait laissé passer la surestimation d'un
  facteur 3 côté V1.

## Ce qui n'est PAS décidé ici

Les deux canaux d'erreur de `query_sql` — refus de garde-fou (`isError=False` + clé `error`) contre
erreur SQL (`isError=True` + code MariaDB) — restent en l'état. Les unifier changerait le contrat
des 27 tools ; c'est documenté, pas corrigé.
